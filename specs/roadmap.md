## 目标与边界

以正在使用的 Prayer 的客服效果为参考，补齐 ForgeBot 功能，保留可扩展、协议中立、资源有界的设计，不复制技术栈或页面数量。

- 保留三种 LLM 协议：Anthropic Messages、OpenAI Responses、OpenAI Chat Completions。
- 保持 Markdown/MDX/TXT 按需结构化检索，将其视作回答前依据收集；不恢复每条消息强制检索。向量适配继续挂起，直到规模和效果证明有必要。
- 不默认持久化完整聊天历史。短期上下文与运营状态存储分别设计。
- 定制业务由 MCP、Skill 或后续插件承载，不写入核心。
- 官方与社区外部插件走同一机制；原生功能仍随唯一核心程序编译，不引入面向用户的定制编译发行矩阵。
- Go 资源优势需实测，不承诺未经同等负载测量的内存、CPU 或延迟改善比例。

## 已确认方向

1. 按功能模块/插件整体挂载；一项功能可以声明多个 Hook、命令和任务。
2. 原生业务模块有配置开关；部署方可关闭后使用自己的外部实现。
3. 核心不检测业务替代完整性、等价关系或能力覆盖；部署方承担替代后的业务行为和副作用。
4. 技术合法性、权限和宿主一致性校验保留，不因取消业务契约检测而移除。
5. 同一 Hook 内原生功能默认先于外部扩展。阶段位置、链内排序和控制权限分开；具体排序算法待设计。
6. 原生与外部实现统一内部挂载模型；Hook 不是用户启停单位。
7. MCP 与 FPP（暂称 Forge Plugin Protocol）协议分离，共用可复用 HTTP/stdio 基础组件；MCP 专属语义保留在其适配层。
8. ConfigStore 是 JSONFileStore、未来 DBStore 上层的接口。现有 settings.Store 已有这一职责，优先演进，不建立平行重复接口。
9. 当前保留 JSONFileStore，不以拆分配置文件或实现数据库存储为前提。

### 不作为当前前置项

- Telegram 为 P1/P2 可后加连接器；OneBot 引用文本、合并转发需要增强，但先明确通用消息模型，再改适配器。
- Web 面板在纯功能和领域接口稳定后另行规划。必要管理 API 随对应功能提供，不必等待完整面板。
- DBStore、多文件配置为低优先级；当前 JSONFileStore 保持可用。
- 插件市场、签名、沙箱、多实例另行评估，不能因讨论过而视为已批准实施。
- 基本错误诊断、资源限制、测试随功能交付，不推迟到最后。引入持久化状态时同步评估备份恢复。
