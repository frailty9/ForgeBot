# 模块级声明式 Hook 挂载需求

日期：2026-09-17。

状态：需求与首期设计已确认，用户已授权连续实施。首版实现和验证见 tasks.md；后续命令、Job、异步观察及 FPP 不在本交付中。

## 1. 目标

作为维护者，希望原生功能与外部插件通过稳定扩展点参与主流程，减少新增功能对核心编排代码的影响。

作为部署方，希望以完整功能/插件为单位启停，可以关闭不合用的原生功能并接入自定义插件，不受业务替代完整性检测限制。

作为维护者，希望配置管理依赖存储接口；当前继续使用 JSONFileStore，未来可新增同级 DBStore 而不侵入业务模块。

## 2. 术语与责任

- 宿主程序：ForgeBot，负责调用、协议、授权、资源和生命周期管理。
- 部署方：选择、配置、运行模块的用户；承担外部替代后的业务行为和副作用。
- 模块：完整原生功能或外部插件，可提供多个处理器、命令、任务。
- Hook：宿主预定义的生命周期接入点，不是用户启停的最小单位。
- 挂载：将获准注册项编排进候选 Runtime，而非握手时直接改变活动链。
- ConfigStore：配置存储接口的概念名称；现有 settings.Store 已承担此职责，是否改名不在需求中强制规定。

## 3. 已确认需求与验收

### R1. 模块级整体挂载

- 当模块声明多个 Hook 时，系统应以同一模块实例组织接入点，而不要求用户分别维护开关。
- 当启用模块时，系统应整体校验并构建其配置要求的注册集合；构建失败不得发布半套新注册。
- 当停用模块时，新请求不应触发该模块处理器或新任务；旧请求及资源按明确退场策略收尾。
- 当模块同时提供命令和定时任务时，系统应将其纳入模块生命周期，不强行伪装成消息 Hook。

### R2. 原生开关与替代自由

- 当部署方关闭可选原生业务模块时，系统应允许停用并保留重新启用所需配置。
- 当原生模块停用且没有外部替代时，系统不应仅因业务能力缺失拒绝配置。
- 当启用外部插件时，系统不应要求声明替代哪个模块，也不检查业务等价、完整性或替代能力覆盖率。
- 当原生与外部实现同时启用时，系统不应因功能相似推断业务冲突；仍可拒绝重复注册标识等技术冲突。
- 停用原生与启用外部可以一起提交，但不强制绑定为替代事务。部署方自行负责行为选择和副作用。

### R3. 宿主保护不等于业务契约检测

- 当模块声明不存在的 Hook、非法协议/数据结构或未获准权限时，系统应拒绝或明确报告。
- 当处理器返回修改时，系统应校验该节点允许的字段和动作，不允许伪造可信身份、提升权限或绕过资源上限。
- 身份可信性、授权、配置事务和生命周期一致性是宿主机制，不作为可关闭业务模块暴露。
- 核心不保证业务等价替换；进程外运行或权限声明也不代表已实现操作系统沙箱。

### R4. 原生与外部统一模型

- 当原生模块由内置注册表声明，或外部模块通过握手声明时，系统应将其转为一致的内部挂载模型。
- 当构建同一 Hook 的处理链时，系统应采用确定性排序，默认原生功能先于外部扩展，不按安装时间排序。
- 不同 Hook 的位置由宿主流程定义；外部模块可以在正确前置节点准备输入，低优先级不等于永远最后执行。
- 模块不得自行提升到宿主保护层；排序不能代替授权或修改后的最终校验。
- 原生代码随单一核心二进制发布，不新增面向用户的编译期第三方插件机制或定制发行版。

### R5. 配置存储接口

- 当配置管理读写配置时，应依赖统一 Store 接口，而非 JSONFileStore 的具体文件布局。
- 当未来新增 DBStore 时，应能作为 JSONFileStore 的同级实现接入；本期不要求实现数据库存储。
- 当前应保留 JSONFileStore，优先演进 settings.Store，不无必要增加平行重复接口。
- 当模块配置改变时，应保留版本冲突检查、候选校验、历史和回滚能力。
- 一个功能只保留一个有效启停来源，不重复要求业务开关与逐 Hook 开关；具体字段迁移在设计阶段确认。
- 模块只接收需要的配置，不直接读取全局文件，不默认获得全局配置或 SecretStore 写权限。
- 如果未来拆分配置文件，Store 仍向上提供一致逻辑快照；本期不以拆文件为前提。

### R6. 热替换与失败保活

- 当模块配置更新时，系统应先构建候选集合，成功后发布；失败保留旧有效配置和运行链。
- 当消息正在处理时，应固定使用所捕获的 generation，不中途混用两套链。
- 当旧模块退场或候选失败时，应释放相关资源，避免遗留任务、处理器和子进程。
- 候选准备应区别于活动运行；未发布时不得因注册而提前发消息或启动业务定时副作用。
- 外部系统副作用无法由配置回滚自动撤销，不承诺通用业务事务回滚。

### R7. 执行有界且可追踪

- 当同步处理器参与流程时，应有明确顺序、失败行为和耗时预算。
- 当异步观察能力启用时，应只读，使用有界排队及明确溢出策略，不无限积压。
- 当处理器失败时，应能定位模块、Hook 和处理实例，不静默包装成成功。
- 原生处理器应遵守取消；超时返回不等于能强制终止任意 Go 代码，不以无限创建 goroutine 伪装隔离。
- 具体失败默认值、排队和并发规则在设计阶段确认。

### R8. MCP、Skill、Plugin 分离

- MCP 继续承载模型工具调用；Skill 继续承载当前支持的文本指令；Plugin 参与宿主功能扩展。
- 后续 FPP 复用可复用的 HTTP/stdio 基础组件，不将 MCP 专属握手、会话头、方法和工具语义作为公共插件契约。
- 插件握手只声明可提供的注册项，由宿主按配置批准，不直接改变活动 generation。
- 本期内部 Hook 考虑未来可序列化边界，但不同时完成外部 FPP 或重构全部 MCP 传输。

### R9. 渐进迁移

- 当使用默认配置且未启用新扩展时，现有功能行为应保持一致。
- 先迁移少量现有可选功能，验证模块级多节点注册、启停与回滚，再迁移其他功能。
- 首个迁移模块在设计阶段选定；验证场景应展示一个模块参与多个节点，不提前承诺所有功能移出核心。
- 测试覆盖排序、受保护字段、整体启停、候选失败、在途请求、资源回收与 Store 测试替身。
- 存储多实现边界可用测试替身验证，不要求引入真实数据库。

## 4. 已取代的旧建议

以下建议已被用户修正，不能据此实施：

- 逐 Hook 启停：改为模块整体启停。
- 外部替代必须通过业务功能契约/覆盖检测：取消。
- 根据相似业务职责强制独占一个实现：不作为通用规则；技术标识冲突另行处理。
- 关闭原生与启用替代必须绑定：取消，允许独立配置。
- 立即拆 JSON 或增加 DBStore：不做；先保证存储接口边界。
- 所有原生功能必须外置：不做，原生模块可留在唯一核心二进制内。
- 用户可任意修改每个处理器阶段、层级、权限：未确认，不默认开放。

## 5. 本期非目标

- 完整 FPP 线协议、插件 SDK、安装器、市场、签名。
- 新 Session、Agent Loop、人工接管或重做反思业务；这些属于后续阶段。
- 新连接器、OneBot 大规模富化、Web 页面。
- DBStore、多文件配置、完整聊天记录持久化。
- 向量检索、操作系统沙箱、通用工作流 DSL。

## 6. 待设计确认

1. 首批 Hook 的精确位置、类型、名称，依据实际 Runtime/Engine 调用链确定，旧示例名不是定案。
2. 首个原生迁移模块，以及跨多个节点整体启停的验证方式。
3. 模块描述、挂载记录、实例生命周期的 Go 接口，不暴露任意内部对象图。
4. 排序、技术命名冲突、允许配置的字段、失败策略；不引入业务替代检测。
5. 现有开关映射与配置迁移；是否保留 settings.Store 命名。
6. 在途请求退场、观察队列、超时取消、准备与激活的精确语义。
7. 为后续 FPP 留边界，但不提前实现整个传输重构。
