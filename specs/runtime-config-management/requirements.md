# 应用层配置热切换需求

## 1. 背景与目标

ForgeBot 后期需要提供 Web 管理面板，使管理员无需登录部署机器终端即可调整应用层行为。配置修改不应被“进程启动时读取一次 JSON”限制；能够原地更新的配置应立即生效，需要重建组件的配置应自动重建，需要重新启动 Bot runtime 的配置应执行可观测的软重启。

本阶段先建立后端配置与运行时边界，为后续 Web 管理面板提供稳定 API 和生命周期能力。
配置分为启动配置与运行时配置：YAML 是正式的启动配置文件，环境变量仅用于覆盖启动字段及注入部署密钥；JSON 文件提供可读写的应用层热更新配置。项目不引入 `.env` 文件约定。

## 2. 用户故事

- 作为管理员，我希望查看当前生效配置及其版本，以便确认 Bot 当前实际使用的参数。
- 作为管理员，我希望修改 LLM 协议、供应商地址、模型和密钥，而无需登录部署机器终端。
- 作为管理员，我希望修改 Gate、Bot 行为、日志等级等应用层配置后自动生效。
- 作为管理员，我希望修改需要重建的配置后由系统执行 Bot runtime 软重启，而不是手动杀进程。
- 作为管理员，我希望非法配置在生效前被拒绝，当前可用 runtime 不受影响。
- 作为管理员，我希望在新配置导致问题时回滚到上一份已生效配置。
- 作为运维人员，我希望知道配置应用是成功、失败、正在重启还是部分降级。

## 3. 配置分类

### 3.1 启动配置（YAML，环境变量可选覆盖）

第一版暂定以下配置只能在进程启动前修改，以 YAML 为正式配置介质，并允许由受控环境变量覆盖：

- HTTP 监听地址；
- 配置持久化文件路径；
- 管理面板认证根密钥及密钥存储后端；
- TLS、反向代理和本机文件系统安全边界；
- 数据库连接、迁移和其他进程级基础设施参数。

静态配置通过管理 API 只读展示；提交修改时必须明确返回“需要重启进程”，不得写入热更新 JSON，也不得伪装成已生效。

### 3.2 应用层热更新配置（JSON）

第一版将以下配置写入独立 JSON 热更新文件，并纳入运行时快照：

- LLM 协议、Base URL、模型、Anthropic 版本、超时及密钥引用；
- Bot 名称及系统指令；
- Gate 参数；
- 日志等级与格式；
- 平台 adapter 的应用层启停开关及策略；
- 后续结构化检索、工具和回复策略配置的扩展位。

JSON 热更新文件必须保持人工可读、可直接编辑和可由 Web 面板原子写回；YAML 不作为本阶段的热写入介质。

LLM API Key 是可热更新的敏感项，但不属于普通运行时配置：

- 管理面板通过独立接口单项写入，读取接口永不返回原值或脱敏尾号；
- `runtime.json` 只保存内部密钥引用和“是否已配置”等非敏感状态，不保存密钥正文；
- 密钥正文由独立 `SecretStore` 持久化，不进入配置快照正文、配置历史、审计内容或日志；
- 更新输入留空表示“不修改”，删除使用独立操作，避免空字符串语义不明；
- 新密钥必须在新 LLM client 构造成功后才切换，失败时继续使用旧版本。

其中：

- 日志等级可原地更新；
- LLM 配置通过重建 `llm.Client` 后原子替换；
- Gate、Bot、平台和检索配置允许通过重建或软重启 runtime 应用。

## 4. 验收标准（EARS）

1. 当进程启动时，系统应先加载并校验启动 YAML 及环境变量覆盖，再加载 JSON 热更新配置，并生成一份带单调递增版本号的有效运行时配置快照。
2. 当管理端读取配置时，系统应返回静态配置、当前运行时配置、版本号、更新时间和应用状态；API Key 等敏感值不得直接返回。
3. 当管理员提交应用层配置时，系统应先执行完整校验；校验失败时不得改变当前生效快照。
4. 当管理员提交仅需原地更新的配置时，系统应在一次应用操作内更新组件，并使后续请求读取新值。
5. 当管理员提交 LLM 配置时，系统应创建对应协议的 `llm.Client`；新客户端创建失败时应保留旧客户端并报告失败原因。
6. 当管理员提交需要重建 runtime 的配置时，系统应停止旧 runtime、等待正在处理的任务到达超时或完成、启动新 runtime，并暴露重启结果。
7. 当配置应用期间发生组件启动失败时，系统应尝试恢复上一份有效快照；恢复失败时必须将 runtime 标记为不可用并提供明确错误。
8. 当管理员提交静态配置修改时，系统应拒绝热应用并提示需要进程重启；不得修改 JSON 热更新文件。
9. 当两个管理请求基于同一旧版本提交时，后到请求应因版本冲突被拒绝，除非显式使用强制覆盖语义。
10. 当管理员请求回滚时，系统应将目标历史快照重新校验并按正常应用流程生效。
11. 当 runtime 正在重启时，系统应返回可查询的状态，不得并发启动两个新 runtime。
12. 当配置变更成功或失败时，系统应记录变更来源、版本、应用动作和结果；日志不得打印完整密钥。
13. 当管理端写入 LLM API Key 时，系统应只接受独立密钥请求；任何普通配置写入中出现 API Key 正文都必须被拒绝。
14. 当管理端读取任意配置、历史或运行状态时，系统不得返回 LLM API Key 正文或可用于还原密钥的内容，只返回是否配置、更新时间和内部状态。

## 5. 非目标

- 本阶段不实现完整前端视觉页面；
- 本阶段不引入数据库，先使用可替换的文件型配置存储接口；
- 本阶段不把启动 YAML 转换回 JSON，也不尝试通过 Web 面板写回环境变量；
- 本项目不加载 `.env` 文件；
- 本阶段不实现所有真实平台 adapter；
- 本阶段不保证不同厂商私有扩展字段的完全覆盖；
- 本阶段不把遗留 MuseBot 配置直接迁入 ForgeBot。

## 6. 约束

- 依赖方向保持为 `cmd -> app -> runtime/settings -> bot/platform/llm`；
- `bot`、`llm` 和平台模块不能自行读取配置文件；
- 配置更新必须是原子可见的；
- 旧配置至少保留一份可回滚历史；
- 未来 Web 面板只能调用管理 API，不得直接操作 runtime 内部对象。
