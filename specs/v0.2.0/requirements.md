## 1. 从 v0.1.0 遗留的明确待做项

### 1.1 自动沉淀重构（BOT-14）

**来源**：v0.1.0 明确留到 v0.2.0 的一项。

v0.1.0 的 `native.knowledge_reflection` 有功能实现，但运营效果未验收，且已决定重构后再验。当前实现的结构性问题：

- 知识沉淀用自己的 24 小时候选问题缓冲（`reflection/buffer`），与新建的核心近期消息容器（`internal/history`）重复。用户在上一版本有意设计了核心容器作为"宿主层的通用结构"，知识沉淀后期重构时也能用上。
- 重构方向：改用 `history.Reader` 和 `History` 的“新消息进入”订阅替换专用的 24 小时候选问题缓冲。模块自己维护答题会话及“答题中/已处理”标记，不依赖“消息移出”事件，不向容器写业务标记或要求钉住记录。
- 重构是破坏式的：`internal/reflection/buffer` 可能整体删除或大幅缩减；模块配置字段（如 `scan_interval`、`quiet_window`、`max_messages_per_conversation`、`max_messages_total` 等）可能变化，需同步更新文档和 `config-index.md`。

**决定：只改缓冲层，不动 pipeline 和 publisher。**

- `reflection/pipeline` 和 `internal/knowledge/markdown` 的业务行为不在本次重构范围内。代码核对发现 pipeline/reflector 引用了 `buffer.AnswerSession`，删除 buffer 前需要迁移纯数据类型；这不扩展为修改提炼、去重或发布算法。
- 删除 `internal/reflection/buffer` 和 `internal/reflection/scanner`，模块改订阅 `history.History` 的 `"new message"` 事件。
- 真正的模型处理仍交给模块自己的定时任务：等安静窗口结束后批量处理已形成的答题会话。删除 scanner 包不意味着取消定时批处理或必然删除 `scan_interval`；原草稿“该字段随包消失”的结论由本次澄清取代。具体配置保留/迁移见设计。
- 重构后运营验收仍需真实群消息窗口，时机与 BOT-14 真实效果验收合并。

**2026-11-10 用户补充原始讨论，恢复以下边界**：

- 管理员引用问题时，先按同群消息 ID 查 history；问题已滑出时，使用适配器已经带回的引用原文。两处都取不到才放弃这一次，不新增取引用消息的远程请求。
- 模块只为已经开始的答题会话保留必要材料：问题文本和 ID、回答文本、第一条回答 ID、起止时间及关联标记。后续同群同一管理员的答复继续归组，不复制所有成员消息等待未来引用。
- 已形成会话的材料由模块保存，问题或回答随后滑出 history 不使该会话失效；处理时不要求重新从容器取得全部正文。
- Core history 继续逐条滑动、通知按一次变化合并、只读且有上限。会话容量与生命周期由模块自己负责，不能把未处理会话钉在容器里。

这取代此前设计草案中“依赖 Evicted 清理会话”“处理前从 Reader 重建全文”“历史记录移出就放弃候选”和“一次删除五个配置键”的方案；外部审批和 QQ 接入等其他范围不由本次补充自动确认。

### 1.3 入群审批外部 HTTP 服务接口（新增）

**来源**：本版新提出。

在现有正则 + 模型判断之外，新增第三种判断方式：调用部署者配置的外部 HTTP 服务，由外部服务返回审批结论。

**配置形式（`native.join_review` 模块 options 顶层）**：

```json
{
  "external_review": {
    "url": "https://example.com/review",
    "method": "POST",
    "headers": { "Authorization": "Bearer {secret_ref}" },
    "body": "{ \"application\": \"{application}\", \"user_id\": \"{user_id}\" }",
    "result_expression": ".approved == true"
  }
}
```

- `url`、`method`：必填
- `headers`：可选，键值对，值支持 `{secret_ref}` 形式引用凭据（不直接写密钥）
- `body`：可选，字符串模板，支持 `{application}`、`{user_id}`、`{conversation_id}` 占位符
- `result_expression`：必填，jq 风格路径表达式，对响应 JSON 求值，结果为布尔值即为审批结论；表达式不合法或响应不可解析时视为拒绝并记日志

**与现有判断的组合**：多个判断启用时，固定按成本升序串行执行：正则 → 外部 HTTP 校验 → 模型判断，跳过未启用项，不并发执行。`combine` 字段（`and`/`or`）对三种方式同样生效，AND 遇 false、OR 遇 true 立即短路，后续判断不再执行；外部服务超时或失败时视为 `unknown`，按 `combine` 语义处理（`and` 时拒绝，`or` 时继续其他判断）。

**安全约束**：
- `url` 必须是 HTTPS（本地测试除外），配置加载时校验
- 请求带固定超时（建议 5s），不得无限等待
- 响应体大小有上限（建议 64KB），超出截断后解析
- `body` 模板的占位符替换在序列化后进行，不产生 JSON 注入

### 1.4 QQ 官方机器人 Connector（新增）

**来源**：本版新提出。

新增 QQ 官方机器人平台适配器，作为独立 ConnectorProvider。QQ 官方机器人（`qqbot`）与 OneBot（`onebot`）是独立的连接器类型，各自注册，不共享实现。

**背景**：QQ 官方机器人 API（原 QQ频道 Bot API，现已扩展到群/私聊）使用 Webhook 或 WebSocket 接收事件，使用 REST API 发送消息，鉴权方式、消息格式和能力边界与 OneBot 有本质区别。

**待设计的核心问题**：
- 接入方式选型：Webhook（需公网或内网穿透）或 WebSocket 长连接
- 消息类型映射：官方 API 的 `MessageCreate`、`MessageMentionEveryone` 等事件到 Core 规范消息的映射
- 能力边界：官方沙盒审核机制、消息被动回复 vs. 主动推送的差异、群与频道的区别
- 鉴权：`appid` + `secret` 获取 Access Token，热更新时 Token 刷新策略

**验收门槛**：与 OneBot 适配器同等要求——能力目录明确标注支持/不支持的操作，不支持的操作隐式失败或返回 unsupported，不抛停止级别错误；至少在真实账号下完成收消息 → 回答的完整链路验收。

**优先级**：中。可与 BOT-19（消息撤回）并行，但不阻塞沉淀重构（BOT-14/ARCH-P06）。

### 1.5 Telegram 群聊 Connector（2026-11-11 新增）

**来源与状态**：用户确认本项纳入 v0.2.0。官方 Bot API 为协议依据，沿用 ForgeBot 的命名、配置约定和接口边界。以下是已确认需求，具体实现方案见设计 §8，任务均未开始。

- **TG-R1 接入与边界**：新增默认关闭的 `native.telegram` Provider，类型为 `telegram`。当启用连接器时，必须只接收显式绑定的普通群及非论坛超级群；私聊、频道、论坛话题不纳入首期。群和消息 ID 以十进制字符串跨接口传递，群内消息 ID 不能被当成跨群唯一标识。
- **TG-R2 两种接收方式**：当部署者选择 `long_polling` 或 `webhook` 时，连接器应只运行对应方式，并自动维护 Telegram 侧登记。切换不得主动丢弃平台待处理更新；不能要求部署者再手工设置另一套接收状态。
- **TG-R3 问答触发**：当收到明确 @本人、回复 Bot 的消息或面向本 Bot 的命令时，应归一为现有问答/命令输入；普通群消息可进入 history 和已启用模块。对其他机器人的命令不得流入本实例的运维命令处理。仅 @其他成员、无关正文不得伪装明确 @Bot。
- **TG-R4 引用与角色**：当 update 自带同群引用原文时，应独立填充 Quoted，不混入当前 Text；不承诺按任意 ID 远端取原文。管理员/群主身份必须来自 Telegram API，查询失败保守视为成员，不能按昵称、正文或匿名占位身份提权。
- **TG-R5 图片输入**：当消息含照片或图片文件时，应有界下载后通过既有媒体模型交给 Core。下载地址含 Bot Token，不得进入模型、history、公开配置或日志；是否调用图片模型继续由 `llm.image_understanding` 决定。
- **TG-R6 文本投递**：发送、欢迎、主动插话和运维通知统一复用 SendTo，首期只发纯文本。超过 Telegram 单条上限时应在请求前明确返回 invalid，不自动拆分、截断或重试。保持 error-only 返回值，不恢复通用回执。
- **TG-R7 新人欢迎**：当绑定群的入群服务消息包含新成员时，应生成现有 MemberJoined 事件，复用 `native.welcome` 的群级开关和纯文本模板；平台重投不得在去重窗口内重复欢迎。
- **TG-R8 单条撤回**：宿主按群取得撤回能力后，应可传消息 ID 调用 Telegram deleteMessage；真实时限和权限交平台判断，不施加新的宿主时限，不新增聊天命令或违规模型。
- **TG-R9 生命周期**：当停止、换代或替换凭据时，应取消收取、排队、下载与处理；失败恢复旧连接器时须按旧模式重新建立接收。入站消息和群事件都不能在切换屏障内误用旧代。
- **TG-R10 可见性与验证**：目录区分本地支持、配置启用、账号权限和实际结果；init/完整示例列出默认关闭的参数，doctor 不发消息、不改远端登记。两种模式分别通过受控测试和真实群聊验收后才可宣称可用。

**明确不做**：Telegram 自动入群审批、申请人问答或 Mini App 验证；私聊、频道、论坛话题；出站媒体、Markdown/HTML 渲染、流式编辑、超长分条、发送重试和完整群历史持久化。不会将用户 bio 代替验证答案接入 `native.join_review`，不实现 Telegram Reviewer，不订阅 chat_join_request。

**部署前提**：一个 Bot Token 由一个 ForgeBot 部署接管接收通道；自动设置/清除 Webhook 可能影响原有接收者，接入教程必须说明独占约束。隐私模式和机器人群权限决定普通消息可见范围，不能把 history/沉淀不可见归因于缓存长度。

## 2. 功能清单中明确列为"下一版本"的项

### 2.1 消息撤回（BOT-19）

**来源**：`docs/feature-inventory.md` BOT-19。

**2026-11-10 用户纠正目标：只提供宿主开放可调用的“撤回一条消息”能力。**

- 取得逻辑群作用域后，传入一个消息 ID 即执行连接器撤回操作；不要求消息仍在 history 中，不读取原文或判断是否违规。
- 取消管理员引用 `/recall` 的聊天入口、聊天角色授权与提示、直接引用 Bot 回复让位增强，以及配套的 history 删除/removed 事件和改绑清理。管理员手动处置使用平台自身功能，不需要绕行机器人。
- 宿主不设统一两分钟限制。即使消息早于 history 保留范围，也可以按 ID 调用；具体平台权限与限制由连接器返回，不能把某个平台的时限当成 Core 规则。
- 暂不规定该能力用于什么：不创建独立定时违规扫描、LLM 工具、决策模型判断或 HTTP 操作入口。未来可附属在已有功能的判断中调用，减少重复模型成本；列举的场景不是实施任务。
- 跨连接器 ID 可能冲突，按逻辑群取得能力保证路由；调用前复核绑定，旧能力遇到改绑/解绑返回 conflict。对模块仅暴露撤回小接口，不暴露 Runtime、存储或任意网络权限。
- 延续此前用户决定：通用发送回执已取消，Sender/ConnectorSender 仍只返回 error；不补写 Bot 平台消息 ID，不新增自身消息回推路径，既有问答记忆与出站正文记录不变。
- 不支持、无权限、平台过期或失败按统一操作语义返回；超时可能已执行，保留执行未知，不自动重试或停止运行时。

这取代本版先前“Option A 管理员引用命令”和相关 BOT-19 回执/让位前置任务，只实现基础操作能力，业务消费方后续设计。

## 3. 路线图 E 阶段：自动沉淀完善

路线图把"自动沉淀完善"列为阶段 E，要求"在已有扫描、去重、发布、索引更新基础上补缺口"。v0.1.0 末段提出的具体缺口：

- 沉淀质量标志：知道哪些内容是由 Bot 自动生成的，哪些经过人工确认
- 知识库版本与撤销：已发布内容的修订和撤销入口

**决定：APP-P07 不纳入 v0.2.0，继续留路线图。** 人工审核闭环依赖稳定的沉淀输出（BOT-14 重构完成后），也依赖某种运营通知机制，先把沉淀重构做完再设计更合适。
