# MD/MDX 结构化检索需求

## 1. 背景与目标

ForgeBot 需要从可配置的本地 MD/MDX 文档库中获取项目事实，但检索不能成为每条消息的固定前置步骤。闲聊、简单问答和管理命令应保持低延迟；只有用户明确要求检索，或 LLM 判断回答确实依赖项目文档时，系统才访问文档索引。

本阶段建立协议中立的检索边界、MD/MDX 解析与本地结构化索引，并把检索作为 Bot 可按需调用的能力接入运行时。向量检索与混合检索仅保留可扩展边界，在文档体量达到需要前不实现、不配置、不产生相关依赖和数据文件。

## 2. 用户故事

- 作为普通用户，我希望闲聊和简单问题不触发文档检索，以免无意义地增加回复延迟。
- 作为项目用户，我希望可以明确要求 ForgeBot 查询文档，并得到带来源信息的回答。
- 作为项目用户，我希望 ForgeBot 在缺少项目事实时能够自行调用检索，而不是凭空猜测。
- 作为管理员，我希望通过运行时配置设置文档根目录、扩展名、结果上限和检索预算，并让修改安全生效。
- 作为管理群成员，我希望通过 `/reload-docs` 重建索引，且重建失败时旧索引继续可用。
- 作为运维人员，我希望查看索引状态、文档与分段数量、最近重载时间及错误，而不暴露文档正文。
- 作为后续开发者，我希望未来增加向量或混合检索时，不修改 Bot 与具体检索实现之间的契约。

## 3. 功能范围

### 3.1 检索策略

首版只支持 `on_demand` 策略：

- 普通消息直接进入 LLM，不执行预检索；
- `/search <query>` 作为显式检索入口，强制执行一次结构化检索；
- 普通对话中，LLM 可以调用受限的 `search_docs` 工具；
- 管理命令由管理路由优先处理，不进入检索或普通 LLM 流程；
- 每轮对话的检索次数、单次超时、结果数量和注入上下文长度均有硬上限；
- 未命中最低相关度时，系统明确返回无结果，不注入弱相关文档。

`policy` 决定是否及何时检索，`backend` 决定如何检索。两者不得混为一个配置项。首版 `backend` 只接受 `structured`，不提供含义不明确的 `auto` 模式。

### 3.2 文档解析

索引器递归读取配置根目录中的 `.md` 和 `.mdx` 文件，并提取：

- 相对路径与文档标题；
- YAML frontmatter 中可识别的标题、描述和标签；
- 标题层级及当前分段的标题路径；
- 正文段落；
- fenced code block 的语言和内容；
- 可在内容未变化时保持一致的分段标识。

MDX 中的 JSX/组件语法不得导致整个文件索引失败。无法安全解释的组件结构可以忽略，但其中可可靠提取的 Markdown 文本仍应进入索引。单个无效文件不得使整次重载丢失原有可用索引；错误应进入重载结果和运行状态。

### 3.3 结构化索引与排序

首版使用进程内本地倒排索引，不引入数据库、向量数据库或 embedding 服务。查询至少支持：

- Unicode 文本规范化和不区分 ASCII 大小写匹配；
- 英文/标识符词项及中文连续文本的可用关键词匹配；
- 标题、标题路径、frontmatter 标签、文件路径、正文和代码字段的差异化权重；
- 多词命中、短语邻近或字段覆盖带来的加分；
- 稳定、可复现的分数与排序；
- 返回命中片段、来源相对路径、标题层级、分数和必要元数据。

索引只能读取文档根目录内的普通文件。符号链接、路径穿越、超限文件和不在允许扩展名内的文件必须按明确规则拒绝或跳过。

### 3.4 运行时与热更新

Search 属于 JSON 运行时配置。至少包含：

- `enabled`；
- `policy`，首版只接受 `on_demand`；
- `backend`，首版只接受 `structured`；
- `document_root`；
- 允许扩展名；
- 默认及最大结果数；
- 单次检索超时；
- 每轮最大检索次数；
- 最大注入上下文长度；
- 最低相关度。

检索器由 `runtime.Manager` 的 generation 持有。配置更新必须先构造并验证候选索引，成功后与新 generation 一并发布；构造失败时不得持久化或替换当前生效配置与索引。禁用检索时允许文档根目录为空，Bot 不暴露检索工具。

`/reload-docs` 只重建当前配置对应的索引，不修改配置版本。新索引完整构建成功后原子替换；失败时旧索引继续服务。重载期间普通对话与已有检索不应被长时间阻塞。

### 3.5 Bot 接入

Bot 只依赖协议中立的检索接口，不导入具体结构化索引实现。检索结果通过独立的上下文构建器转换为 LLM 可用内容，并清楚标记为不可信参考资料，避免文档内容被当作系统指令。

显式 `/search` 与 LLM 工具调用复用同一个检索服务、预算和结果模型。LLM 工具执行循环必须是有界的；工具参数解析失败、预算耗尽、超时或检索失败时，应向模型提供结构化失败结果并终止继续检索，不能形成无限工具循环。

检索故障不应导致普通消息处理长期不可用。只有显式检索请求必须直接向用户说明失败；隐式工具检索失败时允许 LLM 在明确缺少资料的前提下继续回答。

## 4. 验收标准（EARS）

1. 当系统处理不包含显式检索要求的普通消息时，系统不得在首次 LLM 请求前查询文档索引。
2. 当 LLM 未返回 `search_docs` 工具调用时，系统应只完成普通 LLM 调用，不执行检索。
3. 当用户发送合法的 `/search <query>` 时，系统应执行一次结构化检索，并以来源明确的结果作为回答依据。
4. 当用户发送空的 `/search` 时，系统应返回用法错误，不调用 LLM 或检索器。
5. 当普通对话中的 LLM 返回合法 `search_docs` 调用且预算未耗尽时，系统应执行检索并将有界结果返回给 LLM 继续生成回答。
6. 当单轮检索次数达到配置上限时，系统应拒绝后续工具调用并结束检索循环，不得无限请求 LLM 或索引。
7. 当检索超时、参数非法或发生内部错误时，系统应产生可辨识的失败结果；普通对话仍可降级完成，显式检索应向用户报告失败。
8. 当查询结果均低于最低相关度时，系统应返回未命中，不得把弱相关内容注入 LLM 上下文。
9. 当索引 MD/MDX 文档时，系统应保留相对路径、frontmatter、标题层级、正文及 fenced code block 的可检索信息。
10. 当 MDX 文件包含无法解释的 JSX 或组件语法时，系统应尽量索引可靠文本，并将局部解析问题隔离到该文件或分段。
11. 当相同文档集合被重复构建且内容未变化时，系统应产生稳定的分段标识和确定性结果排序。
12. 当文件位于文档根目录外、通过不允许的路径进入、扩展名不受支持或超过大小限制时，系统不得索引该文件。
13. 当启用检索配置时，系统应严格校验策略、后端、根目录和所有预算；首版遇到 `vector`、`hybrid` 或 `auto` 时应拒绝配置。
14. 当管理员提交新的 Search 配置时，系统应先完整构建候选检索器；构建失败时当前配置版本、runtime generation 和旧索引均保持不变。
15. 当 `/reload-docs` 成功时，系统应原子发布新索引并返回文档数、分段数、耗时和完成时间；配置版本不得因此改变。
16. 当 `/reload-docs` 失败时，系统应继续使用旧索引，并向命令发起群组及已启用通知的管理群报告失败摘要。
17. 当管理员读取 runtime 状态时，系统应返回检索启用状态、后端、索引健康状态、文档数、分段数、最近成功重载时间和最近错误，但不得返回文档正文。
18. 当检索内容被加入 LLM 请求时，系统应将其作为有边界、不可信的参考上下文处理，不得允许其覆盖系统指令或工具策略。
19. 当 Search 被禁用时，系统不得构建索引、暴露 `search_docs` 工具或接受 `/reload-docs`，普通对话应继续工作。
20. 当未来增加其他检索后端时，Bot、管理命令和上下文构建器应继续使用同一检索契约，不依赖结构化实现类型。

## 5. 非目标

- 不实现 embedding 生成、向量索引、向量数据库或混合排序；
- 不实现后台文件监视器或每次文件变更自动重载；
- 不抓取远程网站、Git 仓库或数据库内容；
- 不实现全文档管理、在线编辑、上传和删除；
- 不让管理群修改文档根目录或任意 Search 配置；
- 不提供无约束的 agent 工具循环；
- 不承诺首版支持完整 JavaScript/TypeScript 语义级 MDX 执行；
- 不持久化索引文件，进程启动及显式重载时从源文档重建。

## 6. 约束与质量要求

- 依赖方向保持为 `runtime/bot -> search contract`，具体结构化实现不得反向依赖 Bot、LLM、平台或配置存储；
- 文档内容不得写入普通运行状态、管理 API 响应或运维通知；
- 默认配置应优先保证普通对话延迟，检索失败不得扩大为 runtime 全局故障；
- 构建、查询和上下文组装必须具有显式大小、时间及次数上限；
- 测试不得依赖真实 LLM、外部网络或生产文档库；
- Search 配置必须能通过现有版本化 JSON Store 更新、校验、回滚和恢复。
