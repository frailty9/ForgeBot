# 有界 Agent Loop 需求

日期：2026-09-17。

状态：下一阶段需求规划中，尚未确认设计或实施。本文继承 [模块级 Hook 需求](../modular-hooks/requirements.md) 和 [阶段路线图](../roadmap.md)；不能把本文的建议参数视为已实现行为。

## 1. 背景与目标

当前 ForgeBot 的一次回复最多执行一轮工具调用，然后进行一次 LLM 汇总。真实业务问题可能需要串联多个依据来源，例如先查模型列表，再查模型详情或价格。需要将它改为有界的 Agent Loop，使模型可以在同一次用户请求中连续请求工具，同时确保工具、LLM、发送和插件 Hook 都不会无限运行。

目标是提升“依据收集 → 判断 → 继续收集 → 回答”的能力，不是把 ForgeBot 变成无边界自主 Agent，也不是恢复每条消息强制知识库检索。

## 2. 用户故事

- 作为用户，我希望一个问题可以连续调用多个已授权工具，得到组合后的完整回答。
- 作为部署方，我希望可以限制一次请求的总轮数、工具调用数、耗时和响应规模，避免费用、延迟或工具失控。
- 作为部署方，我希望工具、LLM、Hook 或网络故障时，Bot 能明确失败或谨慎沉默，而不是重复调用或发送半成品。
- 作为维护者，我希望每轮工具调用仍经过现有白名单和 `tool.before_execute` Hook，回复仍经过 `reply.before_send` Hook。
- 作为维护者，我希望 Agent Loop 不引入聊天历史持久化；一次 run 的中间消息只在内存中存在，并受有界资源约束。

## 3. 术语

- run：一次从入站消息或 Gate flush 开始，到最终回复、策略性沉默或失败结束的处理实例。
- LLM turn：一次向 LLM 客户端发起的完成请求及其返回结果。
- tool round：一个 LLM turn 返回的一个或多个工具调用经宿主处理并形成工具结果的阶段。
- continuation：携带当前 run 已有消息和工具结果，再次向 LLM 请求下一轮决定。
- terminal result：最终文本、明确不可回答/策略性沉默或有界错误；终止后不得继续工具调用。

## 4. 已确认范围与验收要求

### R1. 有界连续循环

- 当 LLM 返回允许的工具调用且仍有剩余预算时，Bot 应执行工具并将规范化结果追加到当前 run，再请求下一轮 LLM。
- 当下一轮没有工具调用时，Bot 应将其文本视为最终候选回复并结束 run。
- 当达到任一轮数、工具调用数、总耗时或响应大小上限时，Bot 应停止继续调用，并按明确的降级策略结束 run。
- 单次 run 不得因为模型持续返回工具调用而无限循环；上限必须由运行时策略控制并可在 generation 中固定。
- 现有直接请求和 Gate flush 都应使用同一循环语义；两者的 `run_id`、触发来源和效果去重状态仍然独立。

### R2. 工具边界不扩大

- 当模型请求工具时，Bot 应在实际执行前继续检查工具定义、功能开关、调用预算和现有 Hook。
- 未在工具定义或白名单中的调用不得执行，即使 Agent Loop 有剩余预算。
- 每个工具调用必须保留稳定的调用 ID、工具名和规范化结果，供下一轮 LLM 正确关联。
- 工具返回内容仍是不可信数据，不能自动升级为系统指令、配置、身份或权限。
- Agent Loop 不新增 Shell、任意文件、任意网络或 Secret 工具；新增外部能力仍通过 MCP/未来 Plugin 边界注入。
- 结构化检索仍按需触发；普通问题不会因为启用循环而自动检索。

### R3. Hook 语义保持一致

- 每个实际工具调用都应经过 `tool.before_execute`，而不是仅对第一轮调用一次。
- 一个 run 内的检索进度提示最多尝试一次；后续工具轮不得重复发送同类提示。
- 每个最终回复候选、主动回复和进度提示都应经过 `reply.before_send`；Hook 抑制后不得继续发送同一候选。
- `agent.input.prepare` 只处理入站用户内容一次；工具结果和 LLM continuation 不得被当作新的用户输入重复加工。
- Hook 失败、拒绝和终态结果必须在 Loop 中有一致语义；被拒工具应形成可供 LLM 处理的工具结果，不得悄悄丢弃调用 ID。

### R4. 预算与配置

- 运行时应能独立限制：最大 LLM turns、最大工具调用总数、最大单轮工具数、单次 run 总耗时，以及工具结果/中间上下文的最大字节数或字符数。
- 现有搜索专用 `max_queries_per_turn` 的语义不得被无提示地扩大为所有工具预算；迁移字段和兼容策略在设计阶段明确。
- 未填写新预算字段时，应使用保守默认值并保持现有“一次工具回合”行为或明确记录行为变化；不能因零值导致无限制。
- 预算属于 Runtime generation 的不可变策略；一次 run 不因热更新中途改变预算。
- 预算耗尽应记录可定位原因（turn_budget、tool_budget、round_budget、deadline、context_budget 等），不记录密钥和完整敏感上下文。
- 配置校验应拒绝负数、溢出值和相互矛盾的范围；对外管理响应只返回非敏感配置和状态。

### R5. 超时、取消与并发

- 单次 run 应受父 context 和独立总 deadline 双重约束，取更短者；任何 continuation 或工具调用不得绕过父取消。
- 工具调用和 LLM 请求应分别受单步超时约束；单步失败不能自动无限重试。
- 同一 run 内的工具调用是否并行必须由设计确定；无论串行还是并行，都必须有总调用上限、结果确定性和取消传播。
- 不同群组或不同用户的 run 必须相互隔离；一个 run 的预算、Hook 效果、重复检测和临时消息不得泄漏到另一个 run。
- 同一逻辑会话的既有串行/Gate 语义不得因 Loop 继续调用而产生并发回复；与未来 Session Manager 的衔接另行设计。

### R6. 终止与失败降级

- 当模型返回空文本且没有工具调用时，Bot 应返回明确的 `empty_response` 结果，不得再次盲目请求。
- 当 LLM 或工具错误发生时，系统应区分可继续的工具结果错误、不可继续的协议错误、超时、取消和预算耗尽。
- 当已经存在可靠的最终文本时，是否允许在后续工具失败后发送该文本必须在设计中明确；不得将未完成的中间思考或工具参数直接发送给用户。
- 当 Loop 无法得到可靠答案时，Bot 应使用统一的用户可见降级文案、策略性沉默或转人工入口；错误状态必须可观察。
- 到达终止状态后不得再触发工具、LLM continuation 或重复发送；Hook/发送失败不应造成隐式重入。
- 主动介入路径必须继续遵守其谨慎策略，不能因为循环可用就降低可信度门槛或扩大候选发送量。

### R7. 上下文与响应规范化

- 每次 continuation 应以协议中立消息序列表示：用户输入、Assistant 工具调用、Tool 结果和后续 Assistant 消息的关联必须完整。
- 不同 LLM 协议客户端应继续隐藏 wire-format 差异；Loop 不得写入 Anthropic、Responses 或 Completions 专属字段。
- 中间消息和工具结果必须进行大小限制和必要的安全清洗；不能因为工具返回超长内容耗尽整个请求上下文。
- 模型返回的文本只有在被选为最终候选后才能进入 `reply.before_send`；工具调用期间的非最终文本默认不外发。
- 每轮日志应记录 run/generation、turn、tool_count、耗时、预算结果和终态原因，不记录完整提示词、媒体正文、Secret 或未经脱敏的工具敏感 payload。

### R8. Runtime 与热替换

- 当 Loop 策略配置更新时，应通过现有候选 generation 流程构建；构建失败时旧 generation 继续服务。
- 已开始的 run 应固定使用旧 generation 的 Loop 预算、Hook Chain、Tool Executor 和 LLM 客户端；新 run 使用新 generation。
- 旧 generation 退场必须等待已有 run 和 Gate 已启动回调符合现有生命周期约束，再关闭工具执行器和模块资源。
- Loop 本身不得持有全局可变会话历史或跨 generation 的预算计数器。
- 本阶段不引入聊天历史数据库、Session Manager、人工接管数据库或 FPP；这些阶段只消费 Loop 提供的稳定边界。

### R9. 兼容与验证

- 当最大轮数配置为当前兼容值时，已有单工具回归、图片请求、空 @、显式 `/search` 和 MCP 工具行为应保持一致。
- 至少验证：零工具、单工具、多轮串联、多工具同轮、重复工具、未知工具、工具错误、LLM 二次错误、预算耗尽、上下文超限、取消、超时和发送 Hook 抑制。
- 验证不同协议客户端的消息序列等价性，不要求供应商在非标准工具行为下完全一致。
- 验证进度提示最多一次、工具调用 ID 不丢失、Hook 不重复处理用户输入、两群并发隔离以及热更新不混用 generation。
- 运行普通单测、`go test ./...`、`go vet ./...`；竞态测试需在工具链可用时执行并单独记录，不以普通并发测试替代。

## 5. 本期非目标

- Session Manager、长期/跨重启会话记忆和完整聊天记录持久化。
- 人工接管、工单、可信度分类和主动介入策略重做。
- 流式工具调用组装、供应商自动重试/退避策略；已有非工具 SSE 行为不因本阶段被删除。
- 任意工作流 DSL、规划器、子 Agent、自动工具发现、Shell/浏览器沙箱。
- MCP 传输重构、FPP、Plugin 安装和 Hook 外部化。
- 通过新增字段强制每条消息检索或恢复向量检索。

## 6. 待设计确认

1. Loop 默认预算的具体数值、零值含义及与现有 `max_queries_per_turn` 的迁移关系。
2. 同一 LLM turn 返回多个工具调用时是串行还是受限并行；并行时结果排序、取消和进度提示语义。
3. LLM 返回“文本 + 工具调用”时，文本是中间思考、可展示内容还是最终候选；首版建议默认不发送。
4. 工具错误是作为 Tool result 继续交给模型，还是立即终止的分类表；不同错误的 fail-open/fail-closed 策略。
5. 上下文预算按字符、字节、估算 token 还是协议响应限制计算；各协议客户端如何反馈实际 token。
6. 达到预算后已有最终文本的发送策略、统一降级文案、策略性沉默和未来人工接管的接口。
7. Agent Loop 与现有 Hook 的 error/stop/deny/suppress 组合及状态码命名。
8. 是否把 Loop 作为原生模块挂载，还是保留为 Bot Engine 的核心执行器；模块级开关和替代自由需与 Hook 设计一致。

需求确认后，再编写 `design.md` 与 `tasks.md`。在此之前不修改 Agent Loop 代码、不新增配置字段、不改变现有运行时行为。
