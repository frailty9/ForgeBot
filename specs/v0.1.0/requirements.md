# ForgeBot v0.1.0 交付需求

日期：2026-11-03。代码基线：master@c982e73。

状态：用户已于 2026-11-03 授权连续实施并确认 Apache-2.0。2026-11-05 用户审阅后修正三项范围，见下方“2026-11-05 用户决定”，优先于本文其余早期措辞。本文保留需求与最初建议的来源，当前实现及真实环境待验收项见 [任务顺序](tasks.md)，不能用早期草案措辞覆盖后续已实施决策。

## 2026-11-05 用户决定

- **业务范围交给回答模型**：明确 @ 的消息直接发给回答 LLM，由部署者编写的系统提示词（`bot.system_prompt`）决定是否实质回答；`answer_policy` 配置已删除，宿主不再预先分类、拒答或澄清。这避免每条 @ 多一次模型请求，也避免决策故障时用“澄清”文案误导用户。范围约束因此是尽力遵守，需用目标模型实测。
- **删除决策引导预检索**：检索完全由回答模型按工具描述与系统提示词选择。
- **主动插话保留一次决策**：未 @ 时没有用户在等回复，误判即打扰，因此 `native.proactive_reply` 先用一次布尔决策判断“值得主动回答”，并按模块 `scope` 选项判断“属于服务范围”，失败或不确定时沉默。决策模型看不到 system_prompt，所以主动插话的范围单独配置；回答模型另有宿主提示，范围外可输出空内容放弃。
- **入群审批全自动、不留 Bot 侧记录**：由用户提出。入群审核简单但繁琐，自动审批用于阻止试图发布违规内容的人混入；申请人、理由、时间、审批人与拒绝理由由平台（如 QQ）自行记录，Bot 无需重复保存。
- **挂起群公告与消息撤回**：OneBot11 标准没有群公告接口；撤回原意是处理违规消息，但缺少可用的触发方式，暂不交付。

## 1. 产品目标与约束

ForgeBot 是可直接运行、可配置、可扩展的群组 AI Bot。v0.1.0 要形成可重复的“初始化 → 配置模型和渠道 → 问答与工具使用 → 群协作与运维”体验。保留现有模块边界，避免为了形式对称把 Core Agent 扩展搬进普通模块。

- 项目尚未发布，允许破坏式调整配置、接口、数据结构和目录；不为旧设计引入长期兼容层。现有本地文档与凭据仍须保留，破坏式迭代不等于丢弃数据。
- 回答 LLM 必需；决策模型可选；知识来源由部署者挂载工具并指定策略。
- MCP、Skill 保持 Core Agent 扩展入口；知识检索是工具调用的子能力，不在 Engine 建立检索特判。
- 本版本包含 APP-P01、APP-P02、APP-P03、APP-P06、APP-P09（仅入群审批）、新人入群欢迎语和 ARCH-P05 的首期实现及其必要架构支撑。
- FPP、完整 WebUI 延后；公开 SDK、Telegram、SQL/NoSQL 后端、向量检索、沙箱不是本版前置。

## 3. 运行时验收要求

### R1. 回答 LLM 必须配置

- 当 Bot 进入正常运行时，必须存在有效的回答模型配置，且所需凭据可解析；缺少模型或必需认证信息时返回明确的配置错误，不再退化为“ForgeBot received”回显。
- init、doctor、配置编辑、单元测试可在未配置好模型时运行；它们不能因此把 Bot 标记为已就绪。Echo 仍可用于通道测试，但不是无 LLM 的正式回答模式。
- 协议仍限定 Anthropic Messages、OpenAI Responses、OpenAI Chat Completions；需支持无 Key 的本地服务时，应显式声明认证方式，不能将缺少凭据误判为允许匿名。
- 配置缺失与服务暂时不可达分开处理，不以每次启动都请求模型作为唯一校验方式；无效热更新不得替换当前可用配置。

### R2. 图片理解显式开关

- 在回答模型配置中增加 boolean 图片理解声明；建议字段名 image_understanding，建议缺省 false，由初始化向导明确询问或示例明确填写，最终字段在设计中确认。
- 当该开关为 false 且一次已获准处理的问答包含图片时，Bot 直接回复“当前暂不支持图片”，不调用回答模型、决策模型或工具处理该图片，也不先发送检索预回复。
- 当前消息图片与被引用图片都适用；文字＋图片同样不静默丢弃图片后回答，避免用户误以为模型看过图片。
- 当开关为 true 时，继续沿用多模态路径；供应商实际拒绝图片需归一化错误，不把配置声明当作实际能力验证。
- 该分支不改变未 @ 消息准入或让位语义；不能因为收到图片就在本来应保持沉默的群聊中自动回复。

### R3. 表情由适配器尽量文本化

- 当平台表情带有可用的文字描述、规范转义或明确映射时，适配器应转换为有语义的文本，并保留同条消息其他文字、图片和引用。
- Core 不解释平台特有表情 ID/CQ 码；仅把适配后的有效文本作为输入，保留空值及无效媒体防护。
- 没有可靠描述或映射的表情不臆造含义；可忽略或使用明确中性占位，具体策略在适配器设计中固定并测试。

### R4. 工具调用与知识检索

- 当模型请求内置 Tool 或 MCP Tool 时，必须统一经过定义、授权、预算、Hook 和结果回传；知识检索不拥有一条绕过工具链的专用调用路径。
- 官方提供并维护本地结构化检索工具，保留 MD/MDX/TXT 与索引重建能力；部署者可以选择内置工具或自己的 MCP 知识工具，不强制非空本地文档库才能启动。
- 默认按系统提示词和模型工具选择执行检索，不恢复每条消息预检索，也不把“所有技术词”硬编码为业务问题。
- ~~决策引导检索策略~~：2026-11-05 删除。曾实现为“决策要求依据时由宿主先检索一次”，因依赖每条 @ 的范围决策而移除。检索时机由回答模型决定；部署者应在系统提示词中写明知识库覆盖内容、何时必须检索与查不到时如何回答。
- 工具未配置或返回空结果时沿用 Tool 结果语义，不捏造证据。

### R5. 移除非必要非运维命令

- v0.1.0 移除 /search 及其专用注册、直接问答/检索汇总路径、配置说明和相关夹具，检索仍以 Tool 提供。
- 保留 status、pause/resume、restart、proactive、reload_docs 等必要运维命令。未来群管理入口按授权的管理操作设计，不因移除 /search 而删除运维边界。
- 内部通用 CommandRegistration 是否仍有其他消费者应先审计；不为减少一个命令盲目删除有效扩展接口，也不保留只为 /search 服务的穿透依赖。

### R6. 有界连续工具调用（APP-P01）

- 当某次工具结果需要进一步查询时，模型可以在同一次 run 继续请求工具，直到生成最终回答、策略性沉默或明确失败。
- 每次 run 有轮数、工具总数、单轮数量、总时限和中间结果容量上限；取消、Hook 拒绝及失败均有确定终态。预回复最多尝试一次，不展示工具参数或未完成中间文本。
- 每个工具调用与结果保持调用 ID 关联；预算耗尽不隐式重试、不无限追加上下文。主线现有一批调用行为不算该项完成。

### R7. 有界短期上下文（APP-P02）

- 同一群内按用户/对话主体隔离短期上下文，设置 TTL、每会话和全局容量、最大文本/媒体引用规模，以及并发顺序规则。
- 保存必要的问答上下文用于连续追问，不默认保存完整群聊天记录，不持久化工具凭据、图片二进制或所有中间工具 payload。
- 需要明确：成功发送后如何提交上下文、失败/取消是否留痕、同会话并发请求排序、热更新和进程重启后的记忆行为。建议首期进程内短期记忆，重启清空，不让每次无关配置更新静默丢失会话。
- 主动插话仍必须经过独立触发策略；有上下文不意味着未 @ 消息自动获得回复资格。

### R8. 管理员／群主介入后暂停主动插话（APP-P03）

- 当可信管理员或平台群主介入达到配置规则时，按群临时暂停未 @ 主动插话；明确 @ 的回复保留正常准入路径，包含“引用待答问题并 @Bot”的同条消息。
- 必须定义触发依据、暂停时长、延长与恢复规则；不能把管理员任意闲聊自动理解为永久接管。
- 暂停期间未发出的主动回复应在发送前检查并抑制，待处理项不能在恢复时集中补发；此规则不影响明确 @ 的在途请求。
- 平台角色由可信适配器归一化，ForgeBot 配置管理员另保留来源；介入身份不自动等同于宿主配置/凭据管理权限。

### R9. 可选决策模型与逐点回退

- 决策模型作为 Core 决策入口，与回答 LLM 独立配置，支持结构化分类/选择/阈值判断；Jev 是首个候选适配，最终服务与协议在设计中确认，不能假设它兼容现有三种聊天协议。不给决策模型修改权限、直接发消息或直接执行管理动作的能力。
- 首期必须落地明确的决策点：是否主动回复、问题范围/是否需要依据、管理员接答识别。决策服务作为受限的 Core 共享能力，还应可供入群审核等内置功能调用，不只服务聊天路由；沉淀筛选可复用，但文档生成仍由生成模型负责。
- 决策未配置时不得阻断主流程；已配置但超时、不可用、输出无效或低于采用阈值时，必须按下面的逐点规则回退并记录结果，不能统一“全部允许”或统一“全部关闭”。

| 决策点 | 建议缺省／故障回退 |
| --- | --- |
| 明确 @ 的问答 | 2026-11-05 起不调用决策服务；直接交回答模型，范围由系统提示词约束 |
| 未 @ 主动插话 | 仅在群组启用、等待与让位规则允许，且一次决策明确判定值得回答并属于部署范围时执行；其余保持沉默 |
| 管理员介入识别 | 引用待答问题、明确接管指令等确定性信号仍可触发；仅有不确定语义时不伪造肯定判定 |
| 入群审核等副作用 | 没有确定规则或授权人工决定时保留待处理/明确拒绝，不依靠模型故障默认执行 |
| 沉淀筛选 | 未配置决策模型时保留回答 LLM 的现有结构化反思流程；生成/验证失败不发布 |

- 决策阈值和采用策略由本系统控制，不能把返回概率当作正确率保证。相同消息的多个相关判断可复用一次有界决策，避免每个节点都产生新的无上限请求。

#### R9 补充讨论：统一决策契约与单次模型调用

用户提出统一决策请求与结果、未配置 DM 时交给回答 LLM 的方向，已随连续实施落地；以下保留最初约束来源，当前服务、适配和默认预算以 design/tasks 为准。它取代“无 DM 时只依赖规则”的默认路径。

- 统一内部 DecisionRequest / DecisionResult 与按任务版本化的 Schema，不另起一种对外网络协议。DM 与 LLM 适配器接收同一个内部请求，但各自转换为供应商协议，并归一化结果；不假设 Jev 接受任意 JSON Schema 或 Chat Completions 请求。
- 先以有限选择、真假/未知、等级等可映射原语承载实际决策点，不为首版引入任意 Schema 的万能决策引擎。每个任务分别约束允许字段、枚举、必填项和大小。
- 建议路由：确定性规则能解决时直接处理；需要语义判断时，已配置 DM 则优先 DM，否则使用独立提示词的 LLM 决策适配器；结果无效或不可用再按本节已有逐点规则回退。
- Core 提供统一的受限 Decision 服务，可沿既有 capability 注入机制交给主动介入、群审核、反思等消费者。调用方提供任务标识/版本、必要上下文与结果约束，接收归一化结果，不接触模型凭据或具体 DM/LLM 客户端。具体接口留设计阶段确定。
- 任务不硬编码成仅有“是否插话”和“是否检索”两个入口；内置功能可按约定声明自己的决策任务与 Schema，同时受任务注册、输入容量、截止时间、调用次数和并发约束。此开放性不等于开放任意外部网络入口或提前实现 FPP。
- DM 已配置且启用则选择 DM，否则选择 LLM。每次决策最多一个模型请求；选定 DM 后失败直接返回 error，不改用 LLM。布尔入口为 DecideBool(ctx, rule, state) (bool, error)，unknown/低置信结果返回 error，不作为 false。
- LLM 决策只使用有界的必要输入和独立决策提示词，不继承普通回答的 Skill、可执行工具或用户会话角色。复用模型配置/Client 不等于复用聊天会话或把决策结果写入对话记忆。
- 供应商有原生结构化输出时可适配利用；否则使用受约束提示词加严格本地校验，但只能视作尽力生成。结构合法仍需检查任务语义、输入引用和权限，不能把 Schema 校验成功等同于判断正确或授权成立。
- 显式保留 unknown/abstain，避免缺字段默认 false、未知枚举映射到允许值。LLM 自报 confidence 不与专用 DM 的概率混用同一可靠性阈值；来源、回退原因和执行策略由宿主记录。
- 每次决策请求受所属处理实例的总时限、调用预算和并发约束：聊天绑定当前 run，入群申请等事件有独立的有界处理上下文。空值防护、图片禁用和可靠规则已确定的范围可直接处理；不能为了少一次模型请求而让 @ 绕过范围判断，也不能把每个处理节点都变成重复分类请求。
- 选定模型不可用或预算不足则返回错误；业务执行谨慎沉默或不操作，入群申请由管理员在原平台处理，不因模型错误默认同意或拒绝。
- 群审核可复用同一入口判断申请是否符合部署规则；决策结果只提供建议，当前申请有效性、操作权限与自动审批是否已启用仍由宿主执行。欢迎语等确定性模板路径无需强制调用模型。

### R10. 群管理能力（APP-P09）

- Core 提供入群申请事件及同意/拒绝操作的可选接口（群公告与撤回已于 2026-11-05 挂起）；各连接器按支持情况分别实现，不支持者不被迫实现空方法。
- 为首版指定的 OneBot 环境验证可支持的实际调用链，并通过测试连接器覆盖不支持场景；平台支持范围核实后记录，不把所有 OneBot 服务端能力视作一致。
- 上层使用逻辑会话与申请/消息引用，不理解平台私有 ID；支持状态、账号当前权限、配置开关和本次操作结果分别表示。
- 提供授权的运维入口或管理 API；群管理不能只完成接口声明。自动审批默认关闭，支持正则与统一模型判断按 AND/OR 组合；不保存审批记录，无法判断时不操作，不默认将撤回/公告工具开放给 LLM。

## 4. 管理与架构验收要求

### R11. 能力目录、初始化与诊断（APP-P06）

- 管理 API 与 CLI 使用同一只读信息来源，展示模块、连接器、MCP、Skill、回答/决策模型等的类型、来源、配置/启用状态、可用性和最近错误；静态 Skill 的加载状态不伪装为持续连接健康。
- Core 的群管理能力按当前群绑定查询支持情况与权限可知程度；目录不是直接公开内部 capability 容器。
- init 能生成最小静态/运行配置、引导 LLM 和图片开关、凭据初始化；重复运行不得静默覆盖现有配置和密钥。
- doctor 检查配置、Store、目录、凭据引用、端口与工具/渠道可用情况；外部探测显式说明，默认不发群消息或执行审核、公告、撤回。

### R12. 统一操作结果（ARCH-P13）

- Core 边界能按稳定分类和原因码区分成功、合法空结果、忽略/去重/缓冲、未配置、禁用、不支持、未认证、无权限、策略拒绝、目标失效、状态冲突、限流、预算、超时、取消和内部/未知故障。
- 不要求所有内部函数返回同一大结构；保留领域结果与类型化 error，CLI/API/日志/工具结果共享底层语义，不匹配人类错误文案推断类型。
- 有副作用的操作额外表达确认未执行、确认完成、部分完成或结果未知；超时不能推断未执行，重试必须受幂等与预算策略约束。

### R13. 单后端与可扩展的数据结构（ARCH-P05）

- 用户已确认：v0.1.0 交付文件后端；SQL 与 NoSQL 的真实实现留到后续版本。
- 一个运行实例对归入统一持久化体系的数据只选择一个后端类型，由静态配置指定；不允许文件/SQL/NoSQL 同时作为同一数据的权威源，也不在数据库失败后自动降级写本地文件。
- 单后端不等于所有业务共享一个庞大 Store 接口。按职责拆分配置快照读写、版本历史、凭据生命周期、必要运营状态等接口，由同一个被选中的 Backend 组合提供。
- 数据结构使用稳定标识、版本、时间与条件更新语义，避免把文件路径、SQL 查询/事务对象、NoSQL collection 直接暴露给业务调用方。需要的原子性边界按领域聚合定义，并以文件后端契约测试验证；不能默许未来后端降级一致性。
- 静态 YAML 是启动配置；版本化运行配置由选中后端作为唯一权威来源。短期上下文首期驻内存不是第二个持久化后端；日志、导出文档和生成的 Markdown 是明确命名的文件输出，不是隐藏双写 Store。
- Secret 继续加密与只写管理，不因接口拆分改为普通配置可读字段；后端切换要求显式离线迁移或专用流程，不作为应用热更新隐式完成。

### R14. 目录、注释、文档与开源交付

- docs/ 放可公开的使用、部署、排障、架构、决策说明，specs/ 放可维护的版本需求、设计、验收与交接；两者都默认提交 Git，产品文档不依赖用户阅读未完成计划。
- 用户已纠正：space 指 specs/。沿用 docs/ 与 specs/，二者都提交 Git，不新增 space/ 或含糊重复目录；私人实验与运行状态另行隔离，不能混入正式规格。
- configs/ 保留无密钥示例；data/、日志、缓存、索引、临时媒体、个人知识库、自动沉淀的部署数据和本地密钥配置不进入仓库。公开测试夹具与文档示例明确存入受版本控制的目录。
- gitignore 用具体路径/后缀区分共享文档与本地状态；.claude/settings.local.json 等个人配置忽略，共享项目规则是否提交单独判断；不把整个 docs/、specs/ 或全部 JSON/YAML/MD 一概忽略。
- 核心接口、状态机、并发/锁、generation 所有权、回退、权限和副作用边界应有中文解释，说明为何这样设计及约束；不逐行翻译代码，不只改导出符号注释数量。
- 提供 README_ZH.MD 与 README_EN.MD，内容对齐、可复制运行示例和限制说明；根 README.md 保留简短项目入口与语言链接。新 LLM/图片/决策/Store 配置须体现在文档和 init 中。
- 用户已确认 Apache-2.0；添加官方 LICENSE 与必要依赖归属声明。第三方仍保留原许可证，不能声称项目许可覆盖第三方代码。
- 交付门槛包括 go test、go vet、示例配置验证、无决策模型的完整流程、OneBot 真实验收、初始化/诊断、双语启动文档与明确已知限制。竞态测试需在可用环境补验，不把加载失败当作已通过。

### R15. 新人入群欢迎语

- 当连接器报告绑定群的真实成员入群事件且该群启用欢迎语时，按配置发送欢迎消息。入群申请、申请通过与实际入群是不同事件，不在申请阶段提前欢迎。
- Core 定义平台无关的成员入群事件，连接器按支持情况提供事件；不支持成员事件时能力目录明确显示，不能伪造监听能力。
- 建议首期使用按群可配置的确定性模板和有限变量（如新人显示名、群名），不依赖 DM/LLM；模板内容按目标渠道正确转义，支持 @ 提及与否由适配器负责。
- 2026-11-08 修订：欢迎语只做“收到入群事件就发送”，不做持久化去重（部署无需配置存储路径）；历史成员快照、Bot 自己入群不欢迎，默认只欢迎新发生的普通成员入群事件。
- 欢迎语属于成员事件驱动通知，配置开关和主动问答插话策略分开；不因为管理员回答问题就误取消欢迎语，仍服从明确的全局运行和投递规则。
- 首版应验收一个真实连接器的事件到发送链路，并测试不支持、群未启用与发送失败；不增加无需求的群事件自动化平台。

### R16. 部署可配置的业务范围

2026-11-05 修订：范围由回答模型按提示词处理，宿主不做预分类。

- 部署者在 `bot.system_prompt` 中描述业务范围、允许的寒暄与拒答方式；用户输入、引用和历史不能修改它。
- 明确 @、连续追问与引用问题直接交回答模型；不因范围再发分类请求，也不由宿主发送固定拒答/澄清文案。
- 主动插话的范围写在 `native.proactive_reply.scope`，只供其决策使用，应与 system_prompt 保持一致；不在范围内则沉默。
- SoleAPI 是部署者自己的业务范围实例，Core 不写死平台名、行业或拒答清单。
- 这是尽力遵守而非强制保证。验收应用目标模型覆盖：域内问题、域外专业问题、简短但专业的域外问题、寒暄、混合请求，以及主动插话在范围内外的表现。

## 5. 版本推进原则

以下保留版本级先后关系，具体工作包、验收与提交拆分见 [任务顺序](tasks.md)，工程边界与建议默认值见 [实施设计](design.md)。

1. 统一操作结果、Store 领域结构与单后端约束，确定目录边界；形成后续功能使用的最小契约。
2. 回答 LLM 必需、图片开关、适配器表情文本化，移除 /search 的专用行为；先完善输入与默认体验。
3. 有界 Agent Loop 和短期上下文，复用工具与现有模块生命周期。
4. 决策模型与回退、知识工具策略、管理员让位；验证未配置决策模型时仍可正常工作。
5. 群管理事件与可选操作、新人欢迎语，落地一个真实连接器支持矩阵与授权入口。
6. 能力目录、init/doctor；同步完成中文注释、双语文档、许可证与 gitignore，验收 v0.1.0。

群管理只在步骤 5 才拥有动作入口；统一结果与数据结构不是预先建设无限通用框架。FPP、WebUI、Telegram、SDK、数据库后端和向量检索不阻塞本版。

## 6. 初始默认值建议与决策来源

下面保留设计前的建议来源，不是当前待开工清单。用户授权连续实施后选用的工程默认值和验证证据见 design/tasks；后续新需求仍以用户最新决定为准。

- 图片开关字段名与缺省值：建议 image_understanding=false，init 明确询问。
- 知识工具预调用：建议默认关闭，按部署者显式策略与决策结果启用；业务定义由部署者给出。
- 管理员让位时长、可信介入信号与恢复策略；先抑制主动插话，明确 @ 保留。
- 入群审核提供正则与模型 AND/OR 自动审批，默认关闭，人工处理留在平台，不提供 Bot 审批记录或人工入口；群公告与撤回已挂起。
- 决策服务的首期具体实现：设计草案建议先完成通用入口与 LLM 适配，再核对 Jev 接口接入；不把“例如 Jev”理解为排除其他实现。
- 模型决策：统一内部契约与布尔入口；未配置/关闭 DM 时使用 LLM，DM 已启用则故障直接报错。每次最多一个模型请求，无故障后备或重试；供应商输出由适配器严格验证。
- 用户 2026-11-05 修正：@ 消息的范围交给回答模型按提示词处理，不再由宿主预分类拒答；Decision 入口须能供群审核等内置功能复用。任务注册与共享服务边界已有设计草案，尚无对应实现。
- 新人欢迎：建议按群模板默认实现，明确哪些成员事件可触发，不强制依赖生成模型。
- Apache-2.0 已由用户在收尾阶段确认，许可证与依赖归属已落实；本节其余早期建议的实施结果见 design/tasks。
