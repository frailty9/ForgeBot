# v0.3.0 需求草案

日期：2026-11-12。状态：**草案，暂存待确认，未授权实施**。

来源：2026-11-12 v0.2.0 实施期间用户提出的新需求。用户判断这些属于版本外的新增需求，因此不并入已确认的 v0.2.0，另起本版记录。同日用户决定 v0.2.0 以当前验收状态收口，当前版本切至本版；v0.2.0 中未完成的真实验收（外部审批、QQ、Telegram）待条件具备时补验，不阻塞本版。分支方案待用户决定。

本版分两部分：§1 是核心调整，属于前置条件；§2 是反思缺口跟踪，依赖 §1。

## 1. 核心调整（前置）

### 1.1 单轮运行上下文（RUN-CTX）

**现状**（核对 `feat/v0.2.0` 工作区）：`internal/bot/engine.go` 里的 `beginRun` 已经为每次回答创建 `execution`，经 `context.Value` 在本轮内传递，天然按轮次隔离。它目前保存 Hook `Info`、会话租约、历史消息和最终文本，但**不记录工具调用和结果**；轮次结束后数据随之丢弃，模块无法读取。

**需求**：

1. 每轮回答在 `execution` 内累积一份**有界**执行轨迹，至少包括：触发类型与来源消息关联、每次工具调用的名称、参数摘要、结果码、命中数量、失败原因，以及最终输出和结束状态（正常、空回复、被抑制、出错、被取消）。
2. 轨迹由宿主写入，模块只读。不提供模块可任意写入的通用键值袋。
3. 隔离粒度是单轮运行（RunID）。跨轮次的会话级状态仍归 `conversation` 和 `history` 管理，不在本项范围内。
4. 轮次结束时（覆盖正常回复、空回复、抑制、错误、取消），宿主向订阅模块投递一份不可变快照。投递采用只读通知，不进入 Hook 链，不影响回答或发送结果；订阅方慢或出错时不阻塞回答。
5. 条目数量、单项文本长度和总大小都有上限；超限时截断，并在轨迹中标记。

**待确认**：Hook 处理器是否也需要在 `BeforeReply` 等阶段读取本轮已有轨迹（例如据此决定是否抑制）。首期建议不开放，只做结束通知。

### 1.2 模块强制依赖声明（MOD-DEP）

**现状**：`modules.Descriptor` 已有 `Requires` / `Provides` 两个字段，按能力 ID 声明依赖。`Registry.orderedIDs` 加载时会做拓扑排序、检测环，并在提供方未启用时报错拒绝加载（`module X requires unavailable capability "Y"`）。例如：
- `native.knowledge_reflection` 依赖 `search.control.v1`；
- 该能力由 `native.structured_search` 提供。

所以"沉淀依赖检索"这个约束**已经在代码层强制执行**。

**缺口**：

1. 报错只给出能力 ID，没有说明应启用哪个模块。
2. 能力目录、doctor 和模块状态中看不到模块之间的依赖关系，用户只能在启用失败后才发现。

**需求**：

1. 依赖继续由模块代码在 `Descriptor` 中声明，**不放进用户运行时配置**。依赖是实现事实，不应由部署者填写；在配置里写了也不能改变实际依赖。
2. 加载失败时，错误信息需包含缺失能力，以及能提供该能力的已注册模块 ID（例如："启用 native.structured_search"）。
3. 能力目录和 doctor 输出每个模块依赖哪些模块、被哪些模块依赖，管理员在启用前即可查看。
4. 不自动级联启用或停用依赖模块，仍由用户显式开关。

**待确认**：是否需要按模块 ID 直接声明依赖（而非能力 ID）。现有能力 ID 方式允许替换实现，建议保留，只在展示层换算成模块。

## 2. 反思模块的知识缺口跟踪（REFL-GAP）

目标：让 `native.knowledge_reflection` 知道机器人哪些问题没能用现有资料解决，并在知识库更新后核查这些问题是否已补齐。依赖 §1.1 的轮次结束通知。

### 2.1 首期范围

1. **登记**：订阅轮次结束快照。本轮检索正常执行、最终始终没有命中，才登记为待核查候选。检索报错、模型失败、轮次被取消时只记为运行问题，不据此确认缺口；没有检索或只是空回复，也不建立缺口。
2. **持久缺口仓储**：在 `persistence.Backend` 中新增独立领域仓储，存放于知识检索目录之外，跨重启和模块换代保留。记录内容包括：
   - 问题摘要、检索词、有限的来源关联；
   - 首次出现时间、最近出现时间、出现次数；
   - 状态（待补 / 已补齐）；
   - 最近一次核查的索引版本和依据文档。

   同一消息重复投递不增加次数。条目数、单项正文长度、来源数量都有上限，并设保留期；需提供清空和删除单条的方式。
3. **管理员回答关联**：管理员引用某个缺口问题作答时，该答题会话优先进入沉淀批次。发布标准不降低，仍走现有反思、去重和原子发布流程。
4. **索引更新复查**：
   - 检索模块为每次成功发布的索引分配单调递增的代际号，并通知订阅方。覆盖手动重载、沉淀后的重载和配置换代三种来源。
   - 反思模块只记录"待核查的最新代际"，连续多次重建合并为一次。
   - 后台按批次上限，用待补问题重新检索：无命中则保持待补；有命中时交给主 LLM 判断是否覆盖缺失点，确认覆盖才标记已补齐，并记录依据文档。
   - 索引更新失败时，缺口状态保持不变。
5. **可见性**：模块状态接口暴露待补和已补齐的计数与清单。

### 2.2 首期不做

- 用 LLM 归并不同消息中的相似问题，首期只做同一消息去重。
- 判断"命中了资料，但没有覆盖关键部分"。这需要对每个有命中的轮次调用模型，成本和误判风险都高。
- 管理员未引用时，用 LLM 推断回答与哪个缺口相关。
- "现有资料已覆盖但没检索到"时，自动给出文档改进建议。

### 2.3 待确认

- 缺口清单的出口：是否定期推送到管理群，还是只通过状态接口查看（本版 WebUI 仍延后）。
- 后台核查的 LLM 调用预算：每批条数，以及每个索引代际最多核查多少条。
- 问题摘要来自群成员发言，需确定默认保留期。

## 3. 非目标

- 不改变现有回答流程中的自主检索、工具循环和空回复机制。
- 不新增按平台或功能拆分的 runtime 示例；如有新增配置字段，只写入 `configs/runtime.example.json`。
